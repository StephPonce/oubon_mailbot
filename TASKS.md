    - [~] Replace remaining `datetime.utcnow()` usages with timezone-aware equivalents (DEFERRED → new task #39). Audit count: **622 occurrences across 164 files** — 164 SQLAlchemy-column defaults (`default=datetime.utcnow`), 110+ `(datetime.utcnow() - timedelta(...))` cutoff comparisons against non-tz DB columns, 80+ `.isoformat()` JSON serializations, the rest arithmetic/logging. Decision: **do not do this as a scattergun pass**. Three reasons: (1) the dev/prod runtime is Python 3.10, where `datetime.utcnow()` does **not** emit a `DeprecationWarning` — verified by `warnings.filterwarnings('error'); datetime.utcnow()` running clean — so this is prep for a future Python 3.12+ upgrade, not a current test-suite blocker; the `ignore::DeprecationWarning:apscheduler` in `pytest.ini` is only there to silence the third-party library, not first-party code. (2) The SQLAlchemy columns backing these values are `DateTime` (not `DateTime(timezone=True)`), so writing `datetime.now(timezone.utc)` into them strips the tzinfo on the way in and returns a naive value on the way out — any in-Python comparison between a fresh aware value and a round-tripped naive value raises `TypeError: can't compare offset-naive and offset-aware datetimes`. A correct migration has to either (a) move every relevant column to `DateTime(timezone=True)` as an Alembic revision, or (b) wrap every read site with `dt.replace(tzinfo=timezone.utc)` before compare. Either is a dedicated schema pass, not a find-and-replace. (3) The 164 files span every subsystem (auth, billing, advertising, analytics, oi, learning, intelligence, federated, deployment, email_automation, background_jobs, monitoring, testing, platforms, webhooks) — sequencing matters and collapsing this into a Pass 4d checkbox underestimates it. Tracked as **#39 (datetime-tz-migration)** below; the Pass 4d checklist no longer blocks on it. While deferring, verified no first-party code emits a `DeprecationWarning` today by running the full suite under the existing `filterwarnings = error` config: no `datetime.utcnow` warnings in the output.
